# Primary-source evidence for the improvement roadmap

Researched 2026-10-10. Scope: model evidence, interpretation and research lifecycle for the CardioVision AI prototype. These are engineering/research recommendations, not treatment advice or a determination of regulatory status. Sources were restricted to official scikit-learn documentation, BMJ research-methods papers and FDA materials. Recommendations below are applications of those sources to this repository, rather than claims that a source has evaluated this software.

## Repository context

The README describes a 303-record cohort, an internally evaluated release with nested RCA model/threshold selection, and no independent external validation. The Model Quality evaluator already places learned preprocessing inside outer and calibration folds. Patient explanations still come from an independent XGBoost model. These existing improvements should be preserved; the roadmap should not present them as entirely missing. `docs/CLINICAL_VALIDATION.md` still describes these SHAP values as exact and uses stronger governance wording than the README supports. The current release evidence and historical benchmark should remain distinguishable.

## Eight high-value recommendations

1. **Make the intended prediction explicit before improving its score.** Define the intended user, population, measurement timing, inclusion/exclusion rules and outcome definition for CAD/LAD/LCX/RCA. Explain that the retrospective target is a disease class in the supplied cohort; do not imply that the number measures percentage narrowing, future event risk or patient-specific anatomy. Add this compact contract to the demo, reports and model card. FDA's CDS materials recommend making intended use, required inputs, development/validation and patient-specific knowns/unknowns reviewable. This is a transparency design reference, not a claim of exemption or clearance. [FDA CDS review basis](https://www.fda.gov/medical-devices/digital-health-center-excellence/step-6-software-function-intended-provide-clinical-decision-support), [current FDA CDS guidance landing page](https://www.fda.gov/regulatory-information/search-fda-guidance-documents/clinical-decision-support-software).

2. **Protect the entire evaluation from leakage and selection optimism.** Keep imputation, scaling, learned feature selection, calibration and any resampling inside training folds. Put model, hyperparameter, ensemble-weight and decision-threshold selection in the inner loop; evaluate the complete selection procedure on untouched outer folds. Preserve patient/group separation when data contain repeated patients or centers. Freeze the next search protocol and track every experiment to limit repeated adjustment after inspecting outer results. Nested CV addresses selection within that procedure; it cannot erase earlier experimentation on the same cohort. Deliverable: an experiment registry plus reproducible fold/source/configuration manifests. [scikit-learn leakage guidance](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage), [nested versus non-nested CV](https://scikit-learn.org/stable/auto_examples/model_selection/plot_nested_cross_validation_iris.html).

3. **Separate probability quality, class decisions and display colors.** Retain an explicit distinction between model probability, saved classification threshold and 3D display bands. Report held-out Brier score/log loss, reliability plots and bin counts alongside discrimination and threshold metrics. Fitting sigmoid calibration is not evidence of calibration in another population. Keep calibration fitted on predictions from data unseen by the underlying classifier; examine class counts in each split. Do not switch automatically to isotonic calibration on this small cohort: the official guide warns it can overfit with too few samples. Deliverable: a release-bound calibration panel and clear threshold legend, without an assertion that display colors are validated clinical boundaries. [scikit-learn probability calibration](https://scikit-learn.org/stable/modules/calibration.html), [decision-threshold tuning](https://scikit-learn.org/stable/modules/classification_threshold.html).

4. **Report uncertainty and simple baselines before adding complexity.** Compare against a dummy prevalence baseline and a regularized logistic model under the same splits; show per-target positive/negative counts, confusion counts, average precision, sensitivity and specificity. Avoid selecting a winner by accuracy alone. Do not relabel fold dispersion as a confidence interval, and do not use a narrow aggregate interval to imply precise individual risk. Have a statistician specify the uncertainty procedure and its estimand; a future independent validation sample should be sized for desired precision rather than an arbitrary patient count. Deliverable: a paired evidence table with unavailable results explicit. [scikit-learn metrics and baseline guidance](https://scikit-learn.org/stable/modules/model_evaluation.html), [BMJ external-validation sample-size guidance](https://www.bmj.com/content/384/bmj-2023-074821).

5. **Explain the deployed predictor or make the explanation boundary unmistakable.** Keep independent XGBoost SHAP labelled as a separate model's explanation. For a fuller version, evaluate model-agnostic local explanations of the actual released `predict_proba` pipeline, including preprocessing/calibration, and measure approximation stability and cost. Publish the explained model ID, release hash, output units, background/reference data and limitations. As a simpler first step, add held-out permutation importance for the actual predictor; this is global predictive dependence, not a patient explanation or causal effect. Correlated engineered measurements can distort rankings. Deliverable: explanation lineage visible beside each chart and reconciled documentation. FDA transparency principles support explaining the model, performance and limitations; scikit-learn describes held-out permutation importance and correlation caveats. [FDA transparency principles](https://www.fda.gov/medical-devices/artificial-intelligence-enabled-medical-devices/transparency-machine-learning-enabled-medical-devices-guiding-principles), [scikit-learn permutation importance](https://scikit-learn.org/stable/modules/permutation_importance.html).

6. **Make independent external validation the main scientific milestone.** Obtain a separate, appropriate cohort with compatible pre-assessment measurements and independently defined outcomes. Before scoring it, freeze the release, eligibility criteria, endpoints, metric definitions and analysis protocol. Evaluate calibration, discrimination and operating-point performance without tuning on that test cohort. Analyze site/time/population differences; if updating is required, separate updating data from a fresh evaluation set. Deliverable: an external-validation protocol and partner/data-access plan; a new random split of the original workbook does not satisfy this milestone. [BMJ external-validation methods](https://www.bmj.com/content/384/bmj-2023-074820), [BMJ development-to-external-validation framework](https://www.bmj.com/content/384/bmj-2023-074819).

7. **Use TRIPOD+AI to make the evidence package independently reviewable.** Map the 27-item reporting checklist to cohort provenance, predictor/outcome definitions, missingness, sample size, development/evaluation procedures, performance and limitations. Publish protocol, runnable code and model-access details subject to patient-data constraints. Assess relevant subgroup performance with denominators and uncertainty; mark underpowered or unavailable groups explicitly. Involve intended users and patients in defining the workflow and failure cases. The guideline emphasizes transparent reporting, representative data, fairness, stakeholder involvement and open science; checklist completion does not itself establish model quality. Deliverable: a checklist-backed model card/research report rather than an inflated headline metric. [TRIPOD+AI statement, BMJ](https://www.bmj.com/content/385/bmj-2023-078378).

8. **Plan a controlled lifecycle beyond the hackathon.** Maintain versioned immutable model releases, input/output contract checks, traceable assessment/report provenance, rollback and change review. Define a prospective silent-evaluation phase before any workflow-impact study; predefine human-review and failure handling. Monitor missingness, input distribution and performance/calibration when outcomes become available, with site/subgroup review. Set investigation and retraining criteria, then validate each revised release. Deliverable: a lifecycle plan and release acceptance checklist. FDA GMLP describes a total-product-lifecycle approach; its transparency principles emphasize human–AI team performance and information appropriate to intended users. These materials inform engineering planning and do not establish this prototype's legal classification. [FDA GMLP](https://www.fda.gov/medical-devices/artificial-intelligence-enabled-medical-devices/good-machine-learning-practice-medical-device-development-guiding-principles), [FDA transparency principles](https://www.fda.gov/medical-devices/artificial-intelligence-enabled-medical-devices/transparency-machine-learning-enabled-medical-devices-guiding-principles).

## Priority interpretation

For the hackathon: reconcile claims across UI/README/reports, show current-release evidence with explanation lineage, and make the reproducible protocol easy to inspect. For sector leadership: prioritize an appropriate independent cohort, transparent reporting and prospective workflow evaluation over expanding the classifier search space. These priorities are a repository-specific research judgment from the sources above.
